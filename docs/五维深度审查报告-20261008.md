### 1.2 严重问题

####①账本三分裂，全系统互相不对账【P0】

全仓存在**三套并行计费实现**，互不联通：

| 实现 | 存储 | 谁在调 | 写到memberships？ |
|---|---|---|---|
| `core/billing.py` | JSON `data/billing.json` | `web/admin.py` **14 处业务动作** | ❌ 完全独立 |
| `studio/ledger.py` + `gateway/limits.py` | SQLite `ledger` 表 | 网关 `/v1/*` | ✅ |
| `studio/llm_metering.py` | JSON `data/llm_usage.json` | `core/llm.py` | ⚠️ 只扣不发|

实测后果：`/admin/billing` 页面显示的额度，和实际业务能用多少，**不是同一个数**。

更糟的是 `studio/billing_adapter.py` 号称是"桥接层"，但它的 `check_and_deduct` / `redeem_cdkey` **只在 tests 里被调用，生产代码从未 import**——它是死代码。上一轮"修复卡密后门"的改动打在了这个死代码上，所以漏洞至今仍在。

#### ② 卡密兑换是自打开的后门【P0 · 已实测】

`core/billing.py:179-189`：
```python
if code not in cdkeys:                      # 根本不在真实卡密库
    if code.startswith("TOKEN-"):  grant_tokens(100000, ...)   # 编个码就送 10 万
    if code.startswith("PRO-"):    set_tier("pro")             # 编个码就升 Pro
    if code.startswith("MCN-"):    set_tier("studio")          # 编个码就送 600 万
```
外加 `:175` 三个硬编码万能码 `VIP999` / `MEDIAFLOW888` / `PRO2026`，无限次兑换 20 万。

任何登录用户 `POST /api/billing/redeem {"code":"MCN-XXXX"}` 即得最高档。**无限次，无审计。**

#### ③ 扣费返回值 14 处全部丢弃【P0 · 已实测】

```bash
grep -c "billing.check_and_deduct" web/admin.py   # 14
grep -c "if billing.check_and_deduct" web/admin.py # 0
```
`check_and_deduct` 余额不足时 `return False`，但**没有一个调用点检查**。余额耗尽后全部 AI 功能继续执行。这是商业化计费系统的根本性失效。

#### ④ admin 接口越权 + 登录后门【P0】

- `web/admin.py:2266` `/api/billing/admin/gen_keys` 只 `guard(request)`（验登录）**不验 role==admin** → 普通用户批量生成任意面额卡密
- `web/admin.py:271-274` loopback 自动免密，判定条件是 `ADMIN_PASSWORD == "local-admin"`；而 `.env` 里**没有** `ADMIN_PASSWORD`，`core/llm.py:316` 缺失时返回默认值 `"local-admin"` → **该分支当前恒为真**
- `web/admin.py:245` 更狠：`_token()` 是 `sha256("mf|local-admin")` 的**常量**，任何知道算法的人可直接伪造 `mf_token` Cookie 拿超管——**不需要 loopback**

对比 `studio/auth.py:35-41`（密钥缺失即`raise RuntimeError` 拒绝启动）——同一项目里两种相反的安全哲学。

#### ⑤ 前端 XSS / CSRF / 无 CSP【P0】

- `index.html:7857` `toast()` 用 `innerHTML` 渲染后端错误消息，被 20+ 处传入含用户输入的 `j.error` → 可执行任意 HTML（`mobile.html:1906` 用的是 `textContent`，**双端不一致**）
- `index.html:6354-6376` 广告短片 `selling_points`、`hook/body/cta` 全部裸插值进 innerHTML，来源是 LLM 输出（受采集的爆款文章影响，攻击者可控）
- 全仓 `csrf` **零命中**，Cookie `samesite=lax`，无 CSP / 无 `X-Frame-Options` → 结合 XSS 可读Cookie；且**诱导用户 POST `/api/drafts/{id}/publish` 可向公众号/小红书真实发布内容**

#### ⑥ 空壳目录 + 文档宣称【P1】

`studio/agents/`、`studio/drama/`、`studio/copilot/`、`studio/tasks/` **四个目录各只有一个 docstring 文件，无任何实现，全仓零引用**。

但——**这不等于能力缺失**。经核实，真实实现放在 `core/`：

#### ⑦ 任务队列是线程池不是队列【P1】

`core/task_queue.py:114` 直接 `executor.submit`，无 FIFO、无容量上限、无背压、无重试。进度靠**中文关键词猜**（`:215-220` `"完成"→100`、`"压制"→65`）——进度是编造的。且`:263` 反向 `from web import admin` 造成 core→web 循环耦合。

## 二、资深产品经理视角（6/10）

### 2.1 产品定位与能力密度

一句话定位：**「自媒体内容生产全链路 + 大模型 API 中转站」双核**。找选题→写稿→配图→短剧→发布的完整链条，215 条后端路由，前端 176 个 API 调用点。功能密度在国内同类工具里排前列。

### 2.2 核心问题：功能密度过高反而伤害主流程

**PM 的第一判断——这个产品得「选择恐惧症」：**

- 侧边栏 6 个一级入口 + **24 个子标签**（影音工坊独占 7 个、控制中心 8 个）
- 首页 4 张指标卡，其中 **2 张永不更新**：`98.6%`（`index.html:3581`）、`平均评分 88.6 分`（`:3560`）、顶栏算力 `500,000`（`:3318`）、折线图 X 轴写死 `09-15`…`今日 09-21`（`:3631`）

**用户打开产品看到的第一屏是"200+ 热点 / 30 篇成稿 / 12 支成片 / 98.6% 达标率"的假成绩单**，而不是"从这里开始写第一篇"。这不是虚假宣传的问题——**是用户第一天就发现产品在说谎，之后你说的所有数字他都不信了。**

**主流程顺畅度**：极简模式下 `对话→成稿→排版→复制` 是通的（`:8789-8807` 三步引导）；但"找选题→写稿"在全能模式下要穿 3 层（灵感与选题 → 6 个子标签 → 一句话成爆款）。

### 2.4 三套 credits 计价口径，商品模型不成立

`mobile.html:675-690` 有 `☑ 批量管理` + 选中计数 + 批量删除工具条；PC `index.html:4157-4161` 只有"全选 + 删除"，缺多选 checkbox、缺"已选 N 篇"计数、缺失败反馈。**PC 才是重度用户主战场，能力却更弱。**

#### ⑤ 假成功比假失败更伤【P1】

`core/scheduler.py:62`：非小红书平台的定时发布全部执行
```python
db.update_scheduled_post_status(pid, "published", f"[{platform}] 定时任务模拟分发成功完成")
```
DB 写入 `published`，用户以为发出去了。**给假承诺比不给功能伤害更大。**

### 3.3 有价值的东西在日志里【P1】

数据库 364 条选题，全部 `status='pending'`——**362 条从未被消费**。这是长期积累的真实资产，但用户看不到"选题池里还有 362 条没处理"，也没有一键批量处理。

### 3.4 用户视角的稳定性问题

- `core/video.py:79` `tid = f"mf-{draft_id}-{seconds}s-{aspect}"` 无 UUID → 同草稿同参数并发请求**互相覆盖产物**
- 67 处 `except Exception: pass` → 长任务失败时用户看不到原因
- `core/video.py:75` `"口播稿生成失败：" + raw[:150]` —— **把 LLM 原始输出直接抛给用户**，可能含半截 markdown 残片

## 六、跨维度结论：问题的本质

### 6.1 一个根因解释所有问题

**这个项目用"契约文档 + 多 Agent 并行 + 每日集成"的工程方法，去实现一个尚未想清楚商业模式的创作。**

证据链：
1. 立项书 13 项决策全部"✅ 已锁定"，但**没有一条关于定价、渠道、目标用户规模**（`docs/合并立项建议书-V3.0.md`）
2. 代码 6 天写了 34,280 行、195 条路由、215 个功能点
3. 而 `ledger` 表 0 行、`users` 表 1 行、`invites` 表 0 行 —— **从未有一个真实用户完成过一次付费**
4. 于是"计费"变成了三套互相矛盾的实现，"多租户"变成了 `TENANT_ID = "default"`，"会员"变成了三个没定价的额度数字

**工程能力越强，这个偏差越危险**：因为它看起来很完整，团队（包括我自己一开始）很容易把"跑起来了"当成"能用"。

### 6.2 另一个根因：自审机制失效

项目有三份自审文档（`AUDIT_V7.md`/`REVIEW_20261008.md`/`DEDUP_20261008.md`），**六处结论与实测矛盾**，全部给自己打绿。

值得注意的是 `DEDUP_20261008.md:39` **发现过 `image_forge/build_router` 从未被挂载**（本次审查初稿也误判为"未挂载"，实测发现已修）——说明**这个团队的自我审查能力是有的**，但发现的问题没有进入修复闭环，随后文档反而变成了"已全绿"的背书。

**一个靠自审文档维持信心、而自审文档本身不可信的工程，是最危险的状态。**

### 6.3 值得留下的东西（如果只能留5%）

| 资产 | 为什么值钱 |
|---|---|
| `docs/CONTRACT.md` 227 条路由契约 | 全项目最有价值的工程资产，且真有机器门禁在守 |
| `tests/conftest.py` 生产库守卫 + `test_canary.py` seed 哈希 | 想得比多数人细 |
| `core/judge.py` 7 维 Judge | 真调 LLM、真解析、真归一化、真入库 |
