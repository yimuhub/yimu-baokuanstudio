### 1.2 新发现的 P0（全部为本轮实测/复现）

#### ①【P0】users 表时间格式冲突——新注册用户的商业化链路全 500（已复现）

- **现象**（实测）：新注册用户调 `/api/billing/status` → **500 Internal Server Error**；调 `/api/billing/order` → **500 "下单失败，请稍后重试"**
- **堆栈**：`studio/membership/service.py:82` → ORM 加载 User 行 → `TypeError: fromisoformat: argument must be str`
- **根因**（DB 实查）：V6 层（`core/auth.py`）写入 `created_at` 用 **Unix 时间戳浮点**（`1791540446.783243`），V7 层 ORM 的 DateTime 列按 ISO 字符串解析。admin 行是 ISO 格式（`'2026-10-08 03:21:27'`）所以一切正常
- **本质**：这是"两套系统共用一张 users 表"的第三种冲突——R3 修了列集不同，没修**数据格式不兼容**
- **影响面**：所有通过 `/api/auth/register` 注册的用户 = **未来全部真实用户**。他们的会员页、下单、充值，全部 500

#### ②【P0】`/api/schedule/post` 无归属校验（已复现攻击成功）

- **实测**：新注册普通用户 → `POST /api/schedule/post {"draft_id":"<admin的草稿>"}` → **HTTP 200**，成功创建排期 `sch-01b7bb6ff3`
- 攻击者可把**他人的稿件**（包括被合规闸标记 blocked 的违规内容）排期到自动发布链路，或恶意填满他人排期
- 对照：同请求打 `/api/drafts/{did}` 和 `/api/drafts/{did}/share` 均被正确拦截（404"草稿不存在或无权访问"）——说明隔离框架有效，是这一个端点漏接
- 另一个洞：排期接口不检查草稿是否 `blocked` 状态

#### ③【P0-理论】"下单即发可兑换卡密"——当前被 500 挡住，修好 ① 后立即暴露（代码审查确认）

- `commerce.py:115-158`：下单即生成 `status="active"` 的卡密并返回给用户；`billing_adapter.py:187-243` 的兑换**只查 invites 表、完全不查订单是否已付款**
- 攻击链（代码级确认）：注册 → 下单 studio → 拿到 200,000 credits 的 active 卡密 → 兑换到账（价值 2000 元）→ 无限重复
- **为什么实测没打穿**：因为 ① 的 500 把下单本身挡住了。**这是"因祸得福"**——修复 ① 时如果不同时把卡密与订单付款联动，等于亲手打开一个比卡密后门更隐蔽的资损通道（后门靠人发现，这个靠"正常使用"就能薅）
- R3 交付时曾在代码注释里自述这个取舍（"固有取舍"），并说运营核销前人工确认——但把核销确认寄托在人工流程上是不可靠的

#### ④【P0-条件触发】loopback 免密经反代 = 全员超管（本机实测印证）

- `web/admin.py:393` 只看 `request.client.host`，不处理 `X-Forwarded-For`
- **本机实测印证**：审查中所有"未登录"请求都被自动当成 admin（loopback 免密），导致图片直链等测试出现假阴性
- 云端部署只要 nginx 与应用同机，所有公网请求的 `client.host` 都是 `127.0.0.1` → **配置了 ADMIN_PASSWORD 反而把超管开给全网**。fail-closed 逻辑本身是对的，但判定维度错了

## 二、资深产品经理视角（7.0/10，↑1.0）

### 2.1 商业化从 0 到 1 的真实跨越

| 能力 | 7.0.0-dev | 7.1.0 |
|---|---|---|
| 价格 | 全仓无任何售价定义 | 三档明码标价 + 价格页（实测渲染完整） |
| 收款 | 手工发卡密到微信群 | 下单→发码→转账→核销→兑换 全链路 API 化 |
| 退款 | 不存在（全仓零命中） | 按可用余额实际减少量扣回 + 卡密作废 + 审计 |
| 运营后台 | 只有发邀请码 | 用户列表/封禁/发额度/审计查询/漏斗看板 |
| 埋点 | 零 | 5 事件漏斗（实测看板正常） |

**产品判断力上真正的进步是"诚实披露"**：价格页明写"Free 档跑不完一条完整短剧——我们把这一点写在明面上，而不是让你付了钱才发现限制"；升级总览页披露"收款是手工核销""PUBLIC_BASE_URL 未配置"。升级前那个永不变化的 `98.6%` 达标率被清掉，换成真实数据 + 引导态。**7.0 最大的信任赤字（第一屏说谎）在 7.1 被系统性偿还了。**

### 2.2 但产品级失职也很明确

**"没测过真实用户"是本次升级最贵的一课。** 所有 R1~R5 的端到端验收（包括我上一轮自己跑的"下单→核销→兑换 30000 到账"）全部用 admin 账号——而 admin 恰好是全库唯一 ISO 时间格式的用户行。于是：

- admin 视角：一切正常，测试 395 绿
- 任何新注册用户视角：会员页 500、下单 500、**商业化功能等于不存在**

这不是代码问题，是**验收流程问题**：34 项交付、200+ 测试用例，没有一条是"注册一个全新用户然后走完付费流程"。商业化产品的验收第一原则恰恰应该是这个。

### 2.3 免费获客的结构性矛盾已解开，但出现了新矛盾

- 已解开：Free 不再承诺每周 1 条完整短剧（原承诺 9000 消耗 vs 10000 额度）；注册白送 25000 元额度的口子关掉（3000 点真源引用）
- 新矛盾：**Pro 30000 点 ≈ 2 条短剧**，而一条短剧成本 2~8 元、售价 300 元中 2 条短剧的 credits 收入只占 240 元等值——定价数学成立，但"Pro 用户跑完 2 条短剧后做什么"没有设计，续费动机薄弱。图文链路 18 篇/月的产能对重度创作者是够用的，需要在价格页把"图文产能"提到与"短剧"同等的视觉权重

### 2.4 内容合规的产品化程度仍低

合规闸在"成稿"和"发布"两个入口生效，但真实的内容流出路径远不止两条：

| 路径 | 是否过闸 |
|---|---|
| AI 成稿 → approve_and_publish | ✅ |
| 小红书直发（内容来自 `xhs.md` 重排版） | ❌ 全程无闸 |
| 定时排期发布 | ❌ 无闸 |
| 一稿六端裂变产物（LLM 新生成） | ❌ 无闸，且可生成公网分享 |
| 富文本编辑器手动改稿后发布 | ❌ 无闸 |

**审查实测确认了闸本身有效，但 5 条流出路径里 4 条不经过它。** 对运营总监来说这是"体检报告只覆盖 1/5 的体检项目"。且白名单机制是"命中任一短语 → 整篇跳过全部检测"——46 条白名单在公开仓库里，塞一句"健康科普"即可绕过全部 384 条词库。防误伤机制（`safe_terms`）是纯装饰配置，代码从不读取。

**运营总监视角的真实评价：终于有了干活的工具，但工具背后挂着两颗雷。**

### 5.2 雷一：普通用户全 500（见工程师视角 ①）

开闸放用户 = 用户第一脚踩空。**在修好这个之前，launch_mode 里的 `public` 开关必须视为禁用项。**

### 5.3 雷二：合规闸的覆盖率骗局

表面：384 条词库、四级分类、白名单防误伤、实测拦截有效。
实际：**5 条内容流出路径只罩住 1 条**（见产品经理视角 2.4），裂变产物还能变成公网页面。一旦对外投放，运营承担的合规责任并没有因为"有合规闸"而减少多少——这是最危险的"虚假安全感"。

### 5.4 运营数据口径的坑（将在真实运营中爆雷）

- 分享页一次访问调 4 次 resolve，每次 hits+1 → **传播数据虚增 4 倍**
- 频控全局共享：多用户 SaaS 下 A 发满 3 条，B 全被拦 → 客服工单灾难
- 漏斗是"累计触达"不是同会话序列，看板有标注但运营读数时要小心

## 七、最值得记住的三条结论

1. **「测试全绿」与「产品可用」之间隔着"真实用户身份"**——395 项测试全绿，新用户第一脚踩 500。因为所有验收都用了 admin 账号，而 admin 恰好是全库唯一数据格式正确的行。修复方向不是补测试数量，是把"注册全新用户走完主流程"写进 CI。
2. **修一个 bug 可能打开另一个洞**——users 时间格式的 500 目前挡住了"下单即拿卡密"的资损漏洞。修复 500 时若不同时把卡密与付款联动，等于亲手打开比旧后门更隐蔽的通道。
3. **有合规闸 ≠ 有合规**——闸在 5 条内容流出路径里只罩 1 条，白名单一票放行是公开仓库里的万能通行证。对外投放前，覆盖率比词库数量重要。
